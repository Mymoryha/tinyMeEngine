# ADR-0002：最小模块边界与渲染演进

- 日期：2026-11-05
- 状态：Accepted
- 关联任务：M0-002、M1-001；未来 M2/M3

## 背景

需要 Editor、Runtime、窗口和 CLI，但幼年期的目的不是实现完整引擎，而是用最小实现验证可扩展性。渲染算法频繁变化，平台与资源生命周期不应随之重写。

## 选项

1. 单个可执行文件堆所有逻辑：初期快，但 Editor 与算法易耦合，无法独立验证 Runtime。
2. 立即引入多层 RHI、插件和 Render Graph：外观完整，但接口缺乏真实用例，验证与维护成本高。
3. 少量独立 target，共享 Runtime，渲染从具体 D3D12 和显式 pass 起步。

## 决定

选 3。M0 提供两个薄 CLI 入口、共享 app host、纯逻辑会话与测试。没有功能的窗口/Renderer 不伪造空接口。Runtime 不得依赖 Editor；关闭 Editor 后仍可构建运行。

M1 实现窗口与单后端首帧；M2 明确 pass 输入输出、参数和 shader 迭代；M3 用真实算法替换检验边界。Render Graph 只有在至少两个真实管线、重复编排或资源依赖问题出现时才评估。

## 代价与约束

初期会有显式手工编排，不承诺零改动插入任意算法。允许未来调整内部接口；必须记变更和迁移方法。禁止为了避免重构而提前设计全能接口。

M0 `--headless` 专指无 GPU 逻辑测试。未来离屏 GPU 模式另行定义，避免同名参数语义悄悄变化。

## 验证

同一 Session 可被两个入口驱动；CLI 合法/非法路径可自动测试；Editor 关闭构建验证方向。未来实际替换 pass 时统计修改范围，并据此复盘本决策。

## 重审触发

不同实验复制底层代码、资源所有权跨层混乱、Editor 操作无法复用于 CLI、手动 barrier 难以可靠维护。先记录具体痛点再决定抽象。
