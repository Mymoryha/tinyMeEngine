# 项目章程

## 1. 定位与成功标准

TinyMeEngine 是个人主导、人机共建的渲染研究工具。体验、可理解性、可修改性、可验证性优先于功能数量和设备覆盖。学习成果必须能够落到可运行代码、可解释的设计和可复现实验，而不是只有截图。

成功不是“实现多少子系统”，而是：

- 新接手者按仓库说明能完成构建，并知道下一件事及其验收条件。
- 新算法主要修改自己的 pass / shader / 实验配置，不需要改动窗口、Editor 和平台基础设施。
- 同一场景能从窗口交互与命令行路径驱动；无 UI 的执行不意味着必须无 GPU，两者明确区分。
- 性能或视觉结论有输入、参数、测量方法、硬件、版本和参考结果。
- 回看重要设计时能回答“为什么这样做、何时重新考虑”。

## 2. 硬约束与优先级

1. Windows x64，针对已测得的开发机优化；不承担其他系统、GPU 厂商和低配适配。
2. C++20；首后端 D3D12，shader 使用 HLSL，后续引入 DXC 时固定版本。
3. Editor 与 Runtime 共享执行能力；窗口开发与 CLI 开发同等重要。
4. 渲染流程可以被观察、调整、替换。先建立可读的显式 pass 序列，再用实际痛点决定何时需要 Render Graph。
5. 先正确与可诊断，再优化；没有基线不宣布优化收益。
6. 物理仅保留模块演进空间，不提前实现求解器或专用框架。

冲突时优先级：正确性 / 数据安全 → 可理解与接手 → 实验迭代体验 → 当前硬件上的性能 → 功能广度。

## 3. 三个阶段与退出条件

阶段按证据推进，不按日历强行推进。每个里程碑只做一个可展示、可测试的纵向切片。

| 阶段 | 目标 | 退出条件 | 明确不做 |
| --- | --- | --- | --- |
| 幼年期 | 最小实现验证边界 | 构建、窗口、CLI、Editor/Runtime 路径打通；两个不同渲染实验复用同一框架；至少完成一次真实 pass 替换；能定位常见 GPU 错误；记录架构保留/调整结论 | 通用商业引擎能力、资产大平台、全功能 Editor、多后端 |
| 发展期 | 形成稳定基础能力 | 资源与 shader 生命周期、基础场景/相机、基础编辑体验、可观测渲染流程、回归与性能基线能支撑独立 demo；日常实验无需反复修改基础设施 | 追求全品类游戏支持、无限制插件 ABI |
| 铺展期 | 前沿渲染实验与作品 | 每个重点 feature 有方法依据、正确性对照、性能分析、局限；至少一个可独立运行和按说明复现的 demo | 无验证堆特性、只有本机瞬时状态的展示 |

## 4. 幼年期里程碑

| ID | 交付与验收 | 依赖 |
| --- | --- | --- |
| M0 基座 | 权威知识入口、环境基线、ADR、统一构建、独立 Editor/Runtime、无 GPU 测试；两种配置可复现 | 无 |
| M1 窗口与 GPU 首帧 | Win32 窗口 + D3D12 清屏；显式选择并记录 RTX 5080；DPI、缩放、最小化、关闭不挂死；资源安全释放；Debug Layer 零 error/corruption；CLI 可限定帧数退出 | M0 |
| M2 第一条实验链 | 三角形/网格、相机、HLSL/DXC；编辑 shader 后可重编译，失败保留上一个有效版本并给出诊断；CPU/GPU 计时分开；命令行能输出配置和实验结果 | M1 |
| M3 架构试验 | 两种不同 pass 组合和至少一次算法替换；Editor 调参复用 Runtime；无窗口 GPU 路径能复现同一实验；形成架构复盘 ADR | M2 |

不提前承诺 M1–M3 已完成。当前执行队列与实际状态只在 `STATE.md` 维护。

## 5. 演进原则

- **最小不等于随意**：最小实现仍需错误路径、资源所有权、退出方式与验收方法。
- **抽象由证据驱动**：第二个真实使用场景出现时再判断抽象；不同模块可以先用具体类型与简单函数。
- **实验与基础设施隔离**：探索代码允许变化快，但实验结果、失败原因和可复现入口必须留下。
- **可逆决策快速做，不可逆决策先记录**：局部实现自行推进；后端、平台、依赖、资源契约等用 ADR。
- **不以文档数量衡量治理**：每类事实一个权威位置；删除或合并失效的重复说明。

## 6. 范围控制

暂不做：多平台、通用 RHI、多 GPU、网络/联网游戏、音频体系、脚本语言、完整资产数据库、插件热卸载、序列化大框架、物理和大型 ECS。未来真实实验需要时重新评估，不把今天的“不做”当成永久禁令。

所有者负责产品方向、重大取舍和阶段验收；实施者（人或 agent）负责范围内设计、代码、验证和知识闭环。无日期压力时优先缩小变更，避免长时间无法构建的分支。
